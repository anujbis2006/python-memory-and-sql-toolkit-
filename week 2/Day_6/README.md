## 0. Foundation: What is computer memory?

Computer memory is storage that holds instructions and data while a computer
is working. The CPU needs memory because it cannot keep an entire program,
all input data, and every intermediate result inside its small set of
registers.

For example, when a program calculates `price * quantity`, the program
instructions, `price`, `quantity`, and the intermediate result must be
available somewhere. Memory gives the CPU an addressable place to find them.

### A simple analogy

Imagine a library:

- The **books** are program instructions and data.
- The **shelves** are memory locations.
- A **shelf number** is an address.
- The **librarian** is similar to the operating system and memory hardware,
  helping programs access the correct place.
- A small desk beside you is similar to CPU cache: very fast, but limited.

The analogy is useful, but real computers use binary addresses, hardware
translation, permissions, caches, and multiple levels of storage.

### How the CPU interacts with memory

At a high level, the CPU repeatedly:

1. Fetches an instruction.
2. Decodes the instruction.
3. Reads any required data.
4. Executes the operation.
5. Writes the result.

Registers are closest to the CPU. If the required data is not in a register,
the CPU checks cache and then main memory. The operating system arranges the
address space and permissions, while hardware such as the MMU performs
address translation.

### Why memory management is necessary

Memory management is needed to:

- give each process an organized address space,
- prevent one process from corrupting another,
- share memory safely when requested,
- use limited RAM efficiently,
- support programs larger than currently available RAM,
- provide read, write, and execute permissions, and
- reclaim memory when a process ends.

Without management, programs could overwrite the operating system, read other
users' data, or compete unpredictably for the same memory.

# Part 1: Theoretical Foundation

## 1. Virtual Memory and Physical Memory

### RAM and physical memory

**RAM (Random Access Memory)** is fast, volatile storage directly available to
the computer's memory system. Volatile means its contents disappear when power
is removed.

**Physical memory** usually means the actual RAM installed in the machine. A
physical address identifies a location in that RAM. Physical memory is finite:
if a computer has 16 GiB of RAM, it cannot keep unlimited active data in RAM
at the same time.

### Virtual memory

**Virtual memory** is an abstraction in which each process sees its own
virtual address space. A virtual address is not necessarily a direct location
in RAM. The operating system and memory-management hardware translate it to a
physical address.

Virtual memory allows:

- process isolation,
- convenient contiguous-looking address spaces,
- demand loading of pages,
- use of disk-backed storage when appropriate, and
- memory protection.

Virtual memory does not make storage as fast as RAM. If a needed page must be
read from storage, the delay can be extremely large compared with a cache or
RAM access.

### Virtual address versus physical address

| Address | Meaning | Who normally uses it? |
|---|---|---|
| Virtual address | Address generated by a user program | Program and CPU instruction |
| Physical address | Location in actual RAM | Memory controller and hardware |

A process normally works with virtual addresses. User code should not
arbitrarily read physical address `0x1234`; the MMU checks the process's
mapping and permissions.

### MMU and address translation

The **Memory Management Unit (MMU)** is hardware that translates virtual
addresses to physical addresses. It consults translation information prepared
by the operating system, usually page tables, and often uses a TLB cache to
make common translations faster.

```text
CPU generates virtual address
              |
              v
       +--------------+
       | TLB lookup   |
       +--------------+
          | hit / miss
          v
   page table or fault handling
              |
              v
       physical address
              |
              v
             RAM
```

### Process address space and isolation

A **process address space** is the virtual address range and mappings visible
to one running process. It commonly contains regions such as code, read-only
data, writable data, heap, shared libraries, and stack. Exact layout varies
by operating system, architecture, randomization settings, and executable.

Two processes can both use virtual address `0x400000` because that address is
interpreted in the context of each process. Their page tables can map that
virtual page to different physical frames:

```text
Process A: virtual page 7  ----> physical frame 20
Process B: virtual page 7  ----> physical frame 91
```

The process identifier and page-table base determine which mapping is used.
The operating system changes mappings during context switches and hardware
enforces the selected permissions. This is the foundation of process
isolation. Shared memory is possible when the operating system deliberately
maps the same physical frame into multiple address spaces.

### Benefits and limitations

**Advantages**

- Isolates processes from one another.
- Allows sparse and flexible address spaces.
- Supports page-level permissions.
- Makes demand paging possible.
- Lets programs use a large virtual address range.

**Limitations**

- Page tables consume memory.
- Translation adds complexity.
- TLB misses cost time.
- Page faults can be very slow.
- Swapping under memory pressure can cause severe slowdown.
- Virtual addresses do not guarantee physically contiguous memory.

## 2. Paging: pages and frames

**Paging** divides virtual memory and physical memory into fixed-size blocks.

- A **page** is a fixed-size block of virtual memory.
- A **frame** (or page frame) is a fixed-size block of physical RAM.

Pages and frames have the same size, but they are not the same kind of
location. A page belongs to a virtual address space; a frame belongs to
physical RAM.

```text
Virtual address space              Physical RAM
page 0  -------------------------> frame 8
page 1  -------------------------> frame 2
page 2  -------------------------> not present
page 3  -------------------------> frame 5
```

Page sizes are architecture and operating-system dependent. Common systems
use a base page size such as 4 KiB, with some architectures supporting
larger pages. Do not assume one size without checking the platform.

### Page number and offset

For page size \(P\), a virtual address \(V\) can be divided into:

\[
\text{page number} = \left\lfloor \frac{V}{P} \right\rfloor
\]

\[
\text{offset} = V \bmod P
\]

The offset identifies the byte inside the page. Translation changes the page
number to a frame number but preserves the offset:

\[
\text{physical address} = \text{frame number} \times P + \text{offset}
\]

If \(P=4096\) bytes, the offset requires 12 bits because
\(4096=2^{12}\).

### Numerical example 1: page number and offset

Let \(V=13{,}000\) and \(P=4096\):

1. Page number: \(13{,}000 \div 4096 = 3\) remainder \(712\).
2. Offset: \(13{,}000 \bmod 4096 = 712\).
3. The address is therefore page 3, byte offset 712.

If page 3 maps to frame 10:

\[
10 \times 4096 + 712 = 41{,}672
\]

The physical address is 41,672.

### Numerical example 2: number of pages and frames

Suppose a process has a 64 KiB virtual address space and pages are 4 KiB:

\[
\text{pages} = \frac{64\text{ KiB}}{4\text{ KiB}} = 16
\]

If the machine has 256 KiB of RAM:

\[
\text{frames} = \frac{256\text{ KiB}}{4\text{ KiB}} = 64
\]

The process can have up to 16 virtual pages, while physical RAM contains 64
frames. Not all virtual pages need to be resident at once.

### Numerical example 3: translating with a page table

Use page size 1,024 bytes and this page table:

| Virtual page | Physical frame |
|---:|---:|
| 0 | 5 |
| 1 | 2 |
| 2 | 9 |
| 3 | 1 |

Translate virtual address 2,500:

1. Page number: \(2500 \div 1024 = 2\) remainder \(452\).
2. Offset: 452.
3. Page 2 maps to frame 9.
4. Physical address: \(9 \times 1024 + 452 = 9{,}668\).

### Fragmentation

**Internal fragmentation** is wasted space inside an allocated fixed-size
block. If a process needs only 100 bytes of a 4 KiB page, the unused portion
of that allocated page is internal waste.

**External fragmentation** is free space split into small gaps between
variable-sized allocations. Paging avoids most external fragmentation in
physical allocation because any free frame can hold any page. Paging does not
eliminate internal fragmentation, and other allocation systems can still have
their own fragmentation.

## 3. Page tables

A **page table** records how a process's virtual pages map to physical frames.
The operating system creates and maintains it; the MMU uses it during
translation.

A simplified page-table entry (PTE) can contain:

| Field | Purpose |
|---|---|
| Frame number | Physical frame used by the page |
| Valid bit | Whether the virtual mapping is valid for this address space |
| Present bit | Whether the page is currently resident in the relevant memory |
| Read/write permission | Whether reads or writes are allowed |
| Execute permission | Whether instructions may be fetched |
| User/supervisor permission | Whether user-mode access is allowed |
| Accessed/reference bit | Whether the page has been used |
| Dirty bit | Whether it was written since loading |

The precise names and meanings vary by architecture and operating system.
**Valid/invalid** and **present/absent** are related concepts but are not
necessarily identical everywhere. A system may use a valid bit to describe
whether an address is part of the process's legal address space and a present
bit to describe whether its backing page is currently in RAM.

### Single-level and multi-level tables

A single-level page table has one entry for every possible virtual page. A
large address space can make this wasteful, especially when only a small
portion is used.

A multi-level page table divides the virtual page number into indexes:

```text
virtual address
   | top index | middle index | page-table index | offset |
                 |       |             |
                 v       v             v
              directory -> table -> PTE -> frame
```

Unused regions can omit lower-level tables, saving memory. The cost is extra
memory references on a page-table walk when the translation is not in the
TLB. Modern systems may use more than two levels and architecture-specific
formats.

### Complete translation example

Assume:

- virtual address space: 16 KiB,
- physical memory: 32 KiB,
- page/frame size: 4 KiB,
- virtual address: 13,000,
- page 3 maps to frame 6.

There are four virtual pages and eight physical frames. As calculated earlier,
13,000 is page 3 with offset 712. The PTE provides frame 6:

\[
6 \times 4096 + 712 = 25{,}288
\]

The CPU generated virtual address 13,000, but RAM is accessed at physical
address 25,288. The offset stayed the same.

### Page-table overhead

If a process has \(N\) virtual pages and each PTE uses \(E\) bytes:

\[
\text{page-table memory} = N \times E
\]

For a 32-bit address space, 4 KiB pages, and 4-byte PTEs:

\[
N = \frac{2^{32}}{2^{12}} = 2^{20}
\]

\[
2^{20} \times 4 = 4\text{ MiB}
\]

A multi-level design can avoid allocating all lower-level entries for unused
regions.

## 4. TLB (Translation Lookaside Buffer)

The **TLB** is a small, fast cache of recent virtual-page-to-physical-frame
translations. It avoids walking the page table for every memory access.

```text
virtual page number
        |
        v
   +---------+
   |   TLB   |
   +---------+
    | hit       | miss
    v           v
 frame      page-table walk
    |           |
    +-----+-----+
          v
    physical address
```

- **TLB hit:** translation is found quickly.
- **TLB miss:** hardware or the operating system performs a page-table walk.
- **Page fault:** the page-table entry says the page is not currently
  available, so the OS must handle it. A TLB miss does not automatically mean
  a page fault.

After a TLB miss, the system reads the relevant PTE. If the page is present
and permissions allow the access, the translation can be placed in the TLB
and the access continues. If the page is absent, a page-fault exception is
raised.

### Effective access time

Let:

- \(h\) = TLB hit ratio,
- \(t\) = TLB lookup time,
- \(m\) = memory access time,
- \(w\) = extra page-table-walk memory accesses on a TLB miss.

A simple model is:

\[
EAT = h(t+m) + (1-h)(t+(w+1)m)
\]

This is a teaching model. Real CPUs have page-walk caches, parallelism,
different hit costs, and architecture-specific behavior.

### EAT example 1

Let \(h=0.90\), \(t=1\) ns, \(m=100\) ns, and \(w=1\):

\[
EAT = 0.90(1+100) + 0.10(1+2(100))
\]

\[
EAT = 90.9 + 20.1 = 111\text{ ns}
\]

### EAT example 2

Let \(h=0.99\), \(t=1\) ns, \(m=100\) ns, and \(w=1\):

\[
EAT = 0.99(101) + 0.01(201) = 100.0\text{ ns}
\]

A higher hit ratio brings the average closer to the hit cost.

### EAT example 3

Let \(h=0.80\), \(t=2\) ns, \(m=80\) ns, and \(w=2\):

\[
EAT = 0.80(82) + 0.20(2+3(80))
     = 65.6 + 48.4
     = 114\text{ ns}
\]

The exact formula differs across textbooks. Always state your assumptions.

## 5. Page faults

A **page fault** occurs when a process accesses a virtual page that cannot
currently be used as mapped. Often the page is legal but absent from RAM; the
term is therefore not necessarily a programming bug.

### Page-fault handling

```text
CPU references virtual address
            |
            v
PTE says present and permitted?
      | yes                 | no
      v                     v
continue             page-fault exception
                            |
                            v
                 OS checks whether access is legal
                    | legal             | illegal
                    v                   v
              find free frame       terminate/signal
                    |
          no free frame? replace page
                    |
             load page from backing store
                    |
             update PTE and TLB
                    |
             restart interrupted instruction
```

The operating system may:

1. Save the interrupted execution state.
2. Inspect the faulting address and access type.
3. Check whether the address belongs to the process.
4. Find a free frame or select a victim page.
5. Write a dirty victim page back if necessary.
6. Load the required page from its backing source.
7. Update the page table and invalidate/update the TLB entry.
8. Restart the instruction.

### Major and minor faults

Terminology varies by operating system:

- A **major page fault** generally requires relatively slow I/O, such as
  reading a page from disk.
- A **minor page fault** can be handled without disk I/O, for example when the
  page is already available in memory or a mapping can be established.

A page fault becomes a program error when the requested address or operation is
not permitted, such as dereferencing an unmapped address or writing to a
read-only page. The OS may report this as a segmentation fault or access
violation. A legal demand-paged access is handled transparently.

### Page fault versus TLB miss

| Event | Meaning | Typical response |
|---|---|---|
| TLB miss | Translation is not in the fast translation cache | Walk page tables |
| Page fault | Required mapping is absent/invalid or permission failed | Enter OS fault handler |

Every page fault may involve a failed translation lookup, but most TLB misses
are resolved without a page fault.

## 6. Memory protection

Memory protection prevents code from reading, writing, or executing memory
without permission.

Common page permissions are:

- **Read (R):** load data.
- **Write (W):** modify data.
- **Execute (X):** fetch instructions.

The operating system also distinguishes **user mode** from **kernel mode**.
User programs run with restricted privileges. Kernel code runs with permission
to manage hardware and protected resources. Exact mechanisms differ by CPU.

### NX/XD protection

The **NX (No-eXecute)** or **XD (eXecute Disable)** bit marks a page as
non-executable. A typical data page may be `RW` but not `X`; a code page may be
`RX` but not writable. Separating write and execute permissions helps reduce
some code-injection attacks.

### Segmentation fault versus page fault

A page fault is a hardware exception category. It can be recoverable and
normal, such as demand paging. A segmentation fault is an operating-system
report that a process made an invalid or unauthorized memory access. On some
systems it is delivered after a page-fault exception could not be legally
resolved.

```text
valid mapped read      -> continue
valid absent page      -> page fault handler loads it
invalid address        -> fault reported to process
write to read-only     -> protection failure
execute NX page        -> execution protection failure
```

## 7. CPU memory hierarchy

The memory hierarchy puts small, fast storage close to the CPU and larger,
slower storage farther away:

```text
fastest / smallest
        CPU registers
        L1 cache
        L2 cache
        L3 cache
        RAM (DRAM)
        SSD
        HDD
slowest / largest
```

Typical properties:

| Level | Typical role | Sharing and size |
|---|---|---|
| Registers | Current operands and results | Per CPU core, tiny |
| L1 cache | Very frequently used instructions/data | Usually per core |
| L2 cache | Larger backup for L1 | Often per core |
| L3 cache | Shared last-level cache on many CPUs | Often shared, but not universal |
| RAM | Main working memory | Larger, slower than cache |
| SSD/HDD | Persistent storage | Much larger and slower |

Exact sizes, latency, inclusivity, associativity, and sharing arrangements
depend on the CPU and platform. Tables here are conceptual, not universal
hardware specifications.

### Cache hits and misses

A **cache hit** finds requested data in the checked cache. A **cache miss**
requires fetching data from a slower level. Caches are fast partly because
they use SRAM and are physically close to the CPU. Main memory commonly uses
DRAM, which is denser and cheaper per bit but slower and needs refreshing.

### Cache versus virtual memory

| CPU cache | Virtual memory |
|---|---|
| Speeds up data/instruction access | Provides address-space abstraction and protection |
| Hardware-managed at cache-line granularity | OS and MMU manage pages |
| Miss usually fetches from another memory level | Fault may require OS work and storage I/O |
| Does not define process isolation by itself | Central to process isolation |

## 8. Cache locality

**Locality of reference** means programs tend to access a limited region of
memory repeatedly or access nearby addresses.

### Temporal locality

**Temporal locality** means recently used data is likely to be used again:

```python
total = 0
for _ in range(1_000):
    total += important_value
```

The value `important_value` is reused many times.

### Spatial locality

**Spatial locality** means nearby addresses are likely to be accessed soon:

```python
for value in values:
    total += value
```

Sequential traversal commonly benefits because caches fetch a whole cache line,
not just one logical value.

### Row-wise and column-wise access

For a contiguous row-major matrix, this is usually cache-friendly:

```python
for row in matrix:
    for column in row:
        total += column
```

This jumps across rows:

```python
for column in range(number_of_columns):
    for row in range(number_of_rows):
        total += matrix[row][column]
```

The second pattern may have poorer locality in a contiguous row-major layout.
However, Python's `list[list[int]]` is not a contiguous C-style 2D array:
each outer-list element refers to a separate inner list, and each integer is a
Python object/reference. Therefore the difference is influenced by Python
interpreter overhead, pointer indirection, object representation, and memory
layout as well as hardware caches.

This is why the Day 6 program is an educational locality experiment, not a
pure cache benchmark.

# Part 2: The Actual Python Experiment

## What problem does it investigate?

The program creates a 1,000 by 1,000 nested list and computes a sum in two
orders:

1. **Row-wise:** consume each inner row from left to right.
2. **Column-wise:** select one column and visit every row before moving to the
   next column.

Both functions should calculate the same mathematical sum. The experiment
measures whether the traversal order has different elapsed times.

## What is a Python 2D list?

This expression creates a list of row lists:

```python
matrix = [
    [0, 1, 2],
    [3, 4, 5],
]
```

The outer list stores references to two separate inner list objects. It is not
automatically one contiguous block of primitive integers like a C array
`int matrix[2][3]`. Python integers are objects, and the lists store
references to those objects.

## Row-wise traversal

```python
for row in matrix:
    for value in row:
        total += value
```

The outer loop selects a row. The inner loop visits that row's values in
order. It has simple iteration and typically makes good use of nearby
elements within each inner list.

## Column-wise traversal

```python
for col in range(len(matrix[0])):
    for row in matrix:
        total += row[col]
```

The outer loop selects a column index. The inner loop visits that same index
in every row. It repeatedly jumps between separate inner lists. This may have
less favorable locality, but the measured result also includes Python loop,
indexing, bounds-checking, and object-access costs.

## How to interpret the output

The row-wise and column-wise functions should visit the same one million
logical values. The reported duration is the time to execute each function,

operation finished sooner in that run.

experiment includes Python bytecode execution, list iteration, indexing,

## Better experimental method

For a more reliable comparison:

1. Use `time.perf_counter()`.
2. Warm up each function.
3. Run each traversal many times.
4. Use the same matrix for comparable work.
5. Record median, minimum, and spread.
6. Avoid heavy background processes.
7. Keep CPU power and thermal conditions reasonably consistent.
8. Verify both functions return the same sum.

Example benchmark structure:

```python
import statistics
import time


def benchmark(function, matrix, repeats=7):
    function(matrix)  # warm-up
    timings = []
    for _ in range(repeats):
        start = time.perf_counter()
        result = function(matrix)
        timings.append(time.perf_counter() - start)
    return result, statistics.median(timings), timings
```

# Part 5: Connecting Theory with Practice

## What the experiment demonstrates

- **Spatial locality:** traversal order changes which nearby references are
  accessed close together.
- **Sequential access:** row-wise loops consume each inner row sequentially.
- **Memory layout:** nested lists contain references to separate row objects,
  unlike one contiguous primitive matrix.
- **Cache behavior:** locality can influence which data remains useful in
  cache, but this script does not directly count cache hits or misses.
- **Performance measurement:** elapsed time is used as an observable result.
- **Python object representation:** Python-level iteration and object
  references are part of the measured work.

## What it does not demonstrate directly

This script does not directly measure:

- hardware cache misses,
- cache-line size,
- TLB misses,
- page faults,
- physical addresses,
- exact RAM latency,
- branch-predictor behavior, or
- a pure C-style contiguous array traversal.

Hardware performance counters, a controlled native benchmark, and platform
documentation would be needed for those claims. The experiment is valuable as
an educational demonstration of access order and performance, but its result
must not be oversimplified to “the CPU cache did exactly X.”

# Part 6: Interview Preparation

## Level 1 — Basic questions

### 1. What is RAM?

RAM is volatile main memory used for active instructions and data. It is much
faster than persistent storage but smaller and not permanent. **Follow-up:**
What happens to RAM contents after power loss? They disappear.

### 2. What is virtual memory?

Virtual memory gives each process an address space that is translated to
physical memory. It supports isolation, protection, and demand paging.
**Follow-up:** Is virtual memory always faster than RAM? No; it is an
abstraction, and faults can be very slow.

### 3. What is a virtual address?

It is the address generated and used by a program before MMU translation.
**Follow-up:** Is it necessarily a RAM location? No.

### 4. What is a physical address?

It identifies a location in physical memory. The MMU derives it from a
virtual address and page-table mapping. **Follow-up:** Who normally generates
it for user code? The translation hardware.

### 5. What is paging?

Paging divides virtual memory into pages and physical memory into same-sized
frames. A page table maps pages to frames. **Follow-up:** What fragmentation
does paging still have? Internal fragmentation.

### 6. What is a page?

A page is a fixed-size block of virtual memory. **Follow-up:** What is its
physical counterpart? A frame.

### 7. What is a page table?

It stores virtual-page-to-physical-frame mappings and protection metadata.
**Follow-up:** What speeds up access to it? The TLB.

### 8. What is a TLB?

A Translation Lookaside Buffer is a fast cache of recent address translations.
**Follow-up:** What is a TLB miss? A translation is absent from the TLB.

### 9. What is a page fault?

It is an exception raised when a required page is not currently usable or an
access violates mapping rules. **Follow-up:** Is every page fault a bug? No.

### 10. What is memory protection?

It controls which processes and modes may read, write, or execute a page.
**Follow-up:** Name a non-execute mechanism. NX/XD.

### 11. What is a cache?

A cache is smaller, faster storage holding recently or frequently used data.
**Follow-up:** What is a cache hit? Finding requested data in that cache.

### 12. What is temporal locality?

Recently used data is likely to be used again. **Follow-up:** Give an
example. Reusing an accumulator in a loop.

### 13. What is spatial locality?

Nearby addresses are likely to be accessed soon. **Follow-up:** Give an
example. Sequentially reading an array.

### 14. What does `yield` do?

It pauses a generator and returns one value, preserving execution state.
**Follow-up:** How does the generator resume? With `next()` or `send()`.

### 15. Why use `perf_counter()`?

It is designed for measuring elapsed intervals with high resolution.
**Follow-up:** Why not compare only one run? Noise can dominate.

## Level 2 — Intermediate questions

### 1. Why can two processes use the same virtual address?

Each process has a separate page-table context, so the same virtual number can
map to different frames. **Follow-up:** When can they share data? When the OS
maps a common frame intentionally.

### 2. How is a virtual address split?

Into a virtual page number and page offset. The page number is translated; the
offset is preserved. **Follow-up:** What determines offset bits? Page size.

### 3. Why does paging reduce external fragmentation?

Any free frame can hold any page, so variable-sized contiguous holes are not
needed. **Follow-up:** What waste remains? Unused bytes within a page.

### 4. What happens after a TLB miss?

The page table is consulted. A present, permitted entry can be cached in the
TLB; an absent or illegal entry causes fault handling. **Follow-up:** Is it
always a disk access? No.

### 5. How does a page fault get resolved?

The OS validates the access, finds or creates a frame, loads data if needed,
updates mappings, and restarts the instruction. **Follow-up:** What if the
address is illegal? The process receives a fault signal or is terminated.

### 6. Why are page tables multi-level?

They avoid allocating entries for unused address ranges. **Follow-up:** What
do they cost? More lookup steps on a walk.

### 7. What is a dirty page?

A page modified since it was loaded. It must be written back before reuse if
its contents need preservation. **Follow-up:** Which PTE field tracks this?
The dirty bit, where supported.

### 8. Why is row-wise traversal often faster?

It commonly accesses values sequentially within each inner list and reduces
large jumps. **Follow-up:** Is it guaranteed in Python? No; implementation
and workload details matter.

### 9. Why is a Python nested list unlike a C 2D array?

It is an outer list of references to separate inner lists, and integers are
objects. A C row-major array can store primitive values contiguously.
**Follow-up:** What does this add? Indirection and interpreter overhead.

### 10. Why is `time.time()` less suitable for benchmarking?

It represents wall-clock time and can be adjusted. `perf_counter()` is intended
for elapsed timing. **Follow-up:** Is it enough alone? No; repeat runs.

### 11. What does the valid bit mean?

It commonly indicates whether a virtual mapping is legal, but exact semantics
vary. **Follow-up:** Is it identical to present? Not necessarily.

### 12. What does NX mean?

No-eXecute marks a page as non-executable. **Follow-up:** Why use it? To
reduce unintended execution from data pages.

### 13. What is a cache line?

A hardware unit transferred between cache and a lower level. **Follow-up:**
Why does it matter? Nearby data can arrive together.

### 14. What does `if __name__ == "__main__"` do?

It runs a script's entry point only when executed directly, not imported.
**Follow-up:** What is `__name__` during direct execution? `"__main__"`.

### 15. What is a minor page fault?

Usually a fault resolved without slow disk I/O. Exact terminology depends on
the OS. **Follow-up:** What is a major fault? One requiring substantial I/O.

## Level 3 — Advanced questions

### 1. Derive the physical address from page and offset.

Use `frame * page_size + offset`. The offset is unchanged by translation.
**Follow-up:** Why? It identifies position inside the fixed-size block.

### 2. Why can a high TLB hit ratio matter so much?

It avoids page-table walks for most accesses, reducing translation overhead.
**Follow-up:** What else affects EAT? Memory latency and walk depth.

### 3. What happens on a context switch?

The active address-space context changes, and translations may need tagging,
flushing, or replacement. Details depend on the architecture. **Follow-up:**
What helps avoid unnecessary flushes? Address-space identifiers where supported.

### 4. Why can a page fault restart an instruction?

The CPU saves enough state for the OS to resolve the fault; after mapping is
fixed, the instruction can be retried. **Follow-up:** What if it cannot be
resolved? The process is signaled.

### 5. Compare SRAM and DRAM.

SRAM is faster and more expensive per bit and is commonly used for cache. DRAM
is denser and used for main memory. **Follow-up:** Which needs refresh? DRAM.

### 6. Explain multi-level page-table trade-offs.

They save memory for sparse spaces but add walk complexity and memory
references on misses. **Follow-up:** What masks the cost? TLBs and walk caches.

### 7. Why is a column loop not automatically cache-unfriendly in every system?

Data layout may be column-major, rows may fit in cache, and language/runtime
overhead can dominate. **Follow-up:** How test the claim? Control layout and
measure repeatedly.

### 8. Why does comparing `row_time == col_time` not validate results?

It compares performance measurements, not returned sums. Timings are usually
different even when calculations are correct. **Follow-up:** What should be
compared? The returned sums.

### 9. What does a page permission failure look like?

The MMU raises a protection exception; the OS may deliver a segmentation fault
or access-violation signal. **Follow-up:** Is that the same as a missing page?
No.

### 10. Why can swapping cause a performance collapse?

Faults require storage I/O, and repeated eviction/reloading can spend more time
moving pages than executing useful work. This is thrashing. **Follow-up:**
What can reduce it? More RAM, better locality, or reduced working set.

## Level 4 — Practical Python and systems questions

### 1. How would you make this benchmark more reliable?

Use `perf_counter()`, warm up, repeat, record medians, verify sums, and control
background load. **Follow-up:** Why median? It is less affected by outliers.

### 2. How would you fix the result check?

Capture `row_wise_sum(matrix)` and `column_wise_sum(matrix)` and compare the
returned integers. **Follow-up:** Should timing be part of correctness? No.

### 3. What input breaks `column_wise_sum`?

An empty matrix causes `matrix[0]` to raise `IndexError`. Ragged rows can cause
an index error. **Follow-up:** How guard it? Validate dimensions first.

### 4. Why pass `row_wise_sum` without parentheses?

It passes the callable so the timing helper controls when it runs. Parentheses
would execute it before timing. **Follow-up:** What is the passed object? A
function object.

### 5. What does a list comprehension return?

A new list. Nested comprehensions therefore construct a list of lists.
**Follow-up:** Is it lazy? No; use a generator expression for laziness.

### 6. How would you avoid materializing a million-element matrix?

Generate values on demand or use an array library with controlled storage.
**Follow-up:** What trade-off exists? Recalculation or iteration overhead.

### 7. How can you benchmark a contiguous numeric matrix?

Use a suitable native or array representation and document its layout. A
Python list benchmark answers a different question. **Follow-up:** Why?
Representation and runtime overhead differ.

### 8. What is the effect of `time.time()` adjustment during a run?

Elapsed subtraction can be distorted if the wall clock changes. A monotonic
performance clock avoids that category of problem. **Follow-up:** Which API?
`time.perf_counter()`.

### 9. How would you report uncertainty?

Report repeated samples, median, range or percentiles, environment, Python
version, matrix size, and implementation. **Follow-up:** Why include Python
version? Runtime optimizations affect results.

### 10. How do you avoid executing `main()` on import?

Use the `if __name__ == "__main__":` guard. **Follow-up:** Why is import
behavior important? Modules can be reused without side effects.

## Common interview mistakes

1. Saying virtual memory is the same thing as disk.
2. Saying every page fault is a bug.
3. Confusing a page with a frame.
4. Saying a TLB stores data values rather than translations.
5. Treating every TLB miss as a page fault.
6. Claiming paging eliminates all fragmentation.
7. Assuming page size is universal.
8. Ignoring permissions when explaining translation.
9. Claiming one timing run proves cache behavior.
10. Calling Python nested lists contiguous primitive arrays.

## Tricky conceptual questions

1. **Can a page be valid but absent?** Yes, depending on the OS's terminology:
   it can be a legal virtual page whose contents are not resident.
2. **Can two virtual pages map to one frame?** Yes, intentionally or during
   sharing, subject to permissions and OS policy.
3. **Can a page fault happen with a TLB hit?** A TLB entry normally describes a
   usable translation, but implementation details and protection checks vary;
   do not reduce all fault behavior to one simplified rule.
4. **Does a faster row traversal prove fewer cache misses?** No. It is
   consistent with locality but includes many other costs.
5. **Does a generator always use less total memory?** It often lowers peak
   materialization memory, but it still has state and may trade memory for
   recomputation or time.

## Numerical problems with solutions

### Problem 1

Page size is 2,048 bytes and virtual address is 9,000.

\[
9000 \div 2048 = 4\text{ remainder }808
\]

Page number = 4 and offset = 808.

### Problem 2

An 8 KiB virtual space uses 1 KiB pages.

\[
8192 / 1024 = 8
\]

There are 8 virtual pages. If physical memory is 32 KiB, it has 32 frames.

### Problem 3

Page size is 4 KiB, virtual address is 10,000, and page 2 maps to frame 7.

\[
10000 \div 4096 = 2\text{ remainder }1808
\]

Physical address:

\[
7 \times 4096 + 1808 = 30{,}480
\]

### Problem 4

Using \(h=0.95\), \(t=1\) ns, \(m=100\) ns, and one page-table access:

\[
EAT = .95(101) + .05(201) = 106\text{ ns}
\]

### Problem 5

A 48-bit virtual address uses 4 KiB pages. The offset uses 12 bits:

\[
48 - 12 = 36
\]

The virtual page number has 36 bits, representing up to \(2^{36}\) virtual
pages in the simplified full-range calculation. Actual usable ranges depend
on the architecture and operating system.

# Part 7: Speaking and Revision

## 90-second explanation of virtual memory

A computer program uses virtual addresses instead of directly choosing RAM
locations. The operating system gives each process its own virtual address
space, which improves isolation: two programs can use the same virtual number
without sharing the same physical RAM. The MMU translates virtual pages to
physical frames using page tables. A TLB caches common translations so the
translation is fast. If a legal page is not in RAM, a page fault lets the
operating system load it and continue. If the address or permission is
invalid, the process receives an access violation. Virtual memory improves
organization, protection, and flexibility, but page tables consume memory and
page faults can be expensive.

## Three-minute technical explanation of virtual memory

Virtual memory separates the addresses generated by a process from physical
RAM addresses. The address space is divided into fixed-size pages, while RAM
is divided into same-size frames. A virtual address contains a virtual page
number and an offset. The MMU uses the page number to find a page-table entry,
which provides a frame number and permission bits. The offset is preserved, so
the physical address is frame number times page size plus offset.

The TLB caches recent page-to-frame translations. On a TLB hit, translation
is quick. On a miss, the page table is walked. If the page is present and
allowed, the TLB can be updated. If it is absent, a page-fault exception
enters the operating system. The OS validates the address, finds or chooses a
frame, loads the page if necessary, updates mappings, and restarts the
instruction. An illegal address or permission violation cannot be repaired
and is reported to the process. This design provides per-process isolation,
page-level protection, and demand paging.

## Three-minute explanation of CPU cache and locality

CPU caches are small, fast memories between registers and RAM. They work well
because programs usually have locality. Temporal locality means recently used
data is likely to be reused. Spatial locality means nearby data is likely to
be accessed soon. A cache transfers data in lines, so sequential access can
benefit from values arriving together. A row-wise traversal of a contiguous
row-major array typically has better spatial locality than a column-wise
traversal. Python nested lists require a more careful explanation because the
outer list points to separate row lists and values are Python objects.
Therefore a Python timing experiment can show a practical performance
difference, but it does not directly count hardware cache misses. Reliable
conclusions require repeated measurements and controlled representations.

- **DRAM:** Dense main-memory technology requiring refresh.

- **MMU:** Hardware that translates virtual addresses.
- **Page:** Fixed-size block of virtual memory.

- **Spatial locality:** Tendency to access nearby locations.
